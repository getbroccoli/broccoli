# Architecture

This document records the architecture decisions behind Broccoli. It is edited in place; the git history is its change log. Each section states the decision, the reasons and what is deliberately left open.

## Layout of the API

```
packages/api/src/
├── core/          what every module shares: server, database, GraphQL, auth, events
├── modules/       business modules, one folder each, such as company and employees
├── integrations/  clients of external services; return plain data, know no module
└── utils/         helpers that know nothing about Broccoli, such as fetchJson
```

**Import rules.** Each package's `importRules.json` ([API](../packages/api/importRules.json), [web](../packages/web/importRules.json)) lists what each folder, or single file, may import; a target may be a glob (`src/core/*`), and `!` removes matches (`!src/core/server`). Anything not listed is forbidden ([RULE2, RULE3](code-quality.md#modules-and-files)). ESLint enforces it and refuses rules whose graph has a cycle. `core` never imports a module. A folder inside a module may be a module of its own with its own layers, such as `imports/pdfExtraction`; a layer listed as an element keeps its own list instead of its owner's, so `imports/domain` stays below the module that imports it.

## 1. Shape of the system

- **Modular monolith.** One API process, one web single-page app, one container image. The folders of the API are listed above. An integration handles transport (URL, timeout, response format); the rules about the data it returns stay in the module. Integrations use Node's built-in `fetch` through `fetchJson` (timeout, size cap, schema) or `fetchBytes` for images ([RULE22](code-quality.md#layers-and-place)); a vendor SDK is added only where it removes real work.
- **Single-tenant.** One deployment and one Postgres database per company, for self-hosted and managed installs alike. There is no tenant column and no row-level security; the managed service runs one instance per company and migrates each.
- **Layers per module.**
  - `domain`: pure TypeScript, no I/O.
  - `db`: the Postgres adapter. Concrete repositories over the ORM or a transaction (`employeeRepository(db)`) that take and return domain types. Domain facts such as `MappingOutcome` stay in `domain` even when a repository is their first user ([RULE17](code-quality.md#layers-and-place)).
  - `app`: the application layer. `app/useCases/` holds one function per thing a user can do, and a closure-based service for related operations on one subject ([RULE18](code-quality.md#layers-and-place)): the steps of a lifecycle, such as the Slack connection (`createSlackConnectionService`), or independent operations on the same thing, such as reading the import's sources and records (`createImportReadService`). A standalone action stays a use case of its own. Its `index.ts` is the module's use-case factory (`createEmployeeUseCases({ orm })`); it hands each service out whole under its own name (`useCases.files.uploadFile`), never spread among the other use cases. Every business function checks its caller ([RULE19](code-quality.md#layers-and-place)), which is a signed-in user or, for setup, sign-in, init and event handlers, the system; a function another module calls checks the caller itself. Transactions follow [RULE20](code-quality.md#layers-and-place) (§4).
  - `graphql`, `mcp` and `http`: adapters that translate a request into one use-case call; no rules. `http` holds the few routes GraphQL cannot serve, such as images.
  - `index.ts`: the module's public surface; it composes the adapters with the use cases.
  - A `core/` folder that owns state and rules, such as `core/instance` (owner and setup), uses the same layers; its adapter folder is named after its technology (`betterAuth`).
  - **Dependencies point one way** ([RULE16](code-quality.md#layers-and-place)), as the `layers` of `importRules.json` declare. Repositories and services are concrete, with their contract as an interface ([RULE10](code-quality.md#code-shape)), and tests use the real ones ([RULE45](code-quality.md#tests)).
- **Module manifest.** Each module exports one factory, such as `employeesModule({ orm })`, that receives the core's dependencies at startup, builds its use cases once and returns its manifest: SDL and resolvers, event handlers, HTTP routes under `/api/`, later MCP tools and jobs. A factory takes only the core services it uses (`Pick<ModuleDependencies, "orm" | "transact">`) plus its own settings; `createModules` in `modules/index.ts` is the one place that hands them out, so a new dependency touches only the modules that use it. The core iterates over the list of manifests. The GraphQL context carries the security context of the request (its `user` carries the sign-in email for display); resolvers call the module's use cases with it. An event handler calls them with the system's context. No shared request context or central configuration has to be edited to add a module.
- **Cross-module calls** follow [RULE21](code-quality.md#layers-and-place): public functions, which check the caller's security context, or events.
- **Demo data.** The `demo` module holds the sample company and seeds it through other modules' public operations in one transaction; it owns no table. Each module marks its free-standing demo rows `is_demo` and deletes them in its own clear operation; rows an employee owns cascade from the employee. Real rows that reference demo rows block a clear and are never cascade-deleted. The data is a typed list and images inside the module, not a package, until something outside the API reads it.
- **Domain-driven design is tiered** and decided per module when it is designed. The default is a plain domain layer with unit tests. Aggregates, value objects and domain events are used only where invariants demand them, such as leave balances, approvals and permissions.
- **Four primitives.** Every HR feature is built from the same four: **records** (the trusted data), **tasks** (work a person or an agent must do), **calendar** (dates shown from records) and **processes** (what creates tasks when a record changes, a date comes or a task is done). Features built apart each grow their own queue, history and statuses, and merging them later is expensive.
  - **A record is a role, not an engine.** A module's main entity is a record (`employees`, `company`) and keeps its own typed table and SDL. Capabilities records share, such as change history with scheduled changes, custom fields and field visibility, each live in one `core/` folder that modules attach to.
  - **One of each, never one per feature:** one task queue, with approval as a task type; one change history; approvals enforced in use cases, never only in the UI.
  - **Left open:** tasks, calendar, processes and the shared record capabilities are not built yet; each gets its folder, and its details here, with the first feature that needs it. Leave balances and request validation belong to the leave feature, not to a primitive.

## 2. API

- **GraphQL is the primary API and, for now, an internal contract** used by the Broccoli web app. It may change freely before 1.0. The schema is not published and there are no deprecation rules yet.
- **Schema-first SDL.** Each module owns its `.graphql` files and declares its own `type Query` and `type Mutation` fields; they are merged at startup with the core's shared SDL (`Date`, `DateTime`, `PageInfo`). Resolver types come from `@graphql-codegen` into one file, `core/graphql/resolvers.gen.ts`; each module owns its mappers in a build-only `codegen/index.ts` that `codegen.ts` composes. That generated file may reference module types: it is a type-only composition artifact that lint skips, so hand-written core code never imports a module. Generated files (`*.gen.ts`) are not committed: `pnpm codegen` writes them, it runs after `pnpm install`, and every Turborepo task that needs them depends on it.
- **A hairy graph** ([RULE23](code-quality.md#api)), such as `ImportSource.employees` and `ImportEmployee.source`. Components declare their own fragments, and fragments only work when types link to each other; a tree that is read through the root is REST with another syntax.
- **Mutations return a payload** ([RULE24](code-quality.md#api)): a type of its own when the mutation can fail in an expected way, so its fields and its error grow without touching another mutation. The payload carries the changed object, or the parent after a removal, so the client selects what it needs in the same request instead of refetching. A payload may add `query: Query!` when a client must refresh other data in the same request; the resolver returns an empty object for it and the `Query` resolvers answer. None needs it yet. The `broccoli/mutation-payloads` lint rule in `packages/config` checks the API's merged SDL, so `pnpm check` refuses a mutation that breaks the shape. A resolver builds its payload with `mutationPayload<ResolversTypes["CompanyUpdatePayload"]>("company", …)`. The type argument is codegen's resolver type for the payload, with each module's mappers applied (the plain `CompanyUpdatePayload` type is the GraphQL shape, which a mapped type such as `Import` does not return), so `tsc` refuses a misspelled field or a result of the wrong type. TypeScript has no exact types, so without it a misspelled field next to `error` would compile and return `null`.
- **No N+1** ([RULE25](code-quality.md#api)). A DataLoader batches the keys into one query (`where id = any(...)`, or a `group by` for counts). Modules own their DataLoaders and batch through their use cases; `perRequest(create)` in `core/graphql` gives each request its own set.
- **Namespaced mutations** group operations by module (`absence { request(...) }`). Because the GraphQL specification only guarantees serial execution for root mutation fields, and the fields inside a namespace run in parallel, the server lets a mutation select one namespace and one operation in it; client documents are not linted for it.
- **Errors.** Errors raised before execution (parse, validation, bad input) reach the client as they are. A mutation's expected failure is its payload's `error` ([RULE27](code-quality.md#api)), so the schema lists what can go wrong and a client reads it as data. Use cases report it with an `ApplicationError`, which the resolver turns into an error type: `INVALID_INPUT` into `InvalidInputError` with its fields (`{ field: "email", code: "taken" }`), `CONFLICT` into `ConflictError` when the data is not ready for the operation yet, such as approving while a file is still being read, and `UNAVAILABLE` into `UnavailableError` when an external service such as Slack refused or failed. `error` is one field: when one run must report several distinct failures, such as a batch with conflicting and invalid rows, its union gains a `CompositeError { message, errors: [Error!]! }`. `UNAUTHENTICATED` and `FORBIDDEN`, and any failure of a query, reach the client as a GraphQL error with the code in `extensions`. Any other error is masked.
- **Pagination.** Lists are Relay connections (`first`, `after`; `edges { cursor node }`, `pageInfo { hasNextPage endCursor }`) over keyset queries. Cursors are opaque base64url strings of the sort key and the id, prefixed with the order they belong to, so a cursor from another order is refused. `first` defaults to 100 and is at most 10,000. `core/pagination` parses page arguments and builds connections; `core/db` builds the keyset condition. Lists take `orderBy: { field, direction }` and a `filter` input; `keysetOrder` always ends the order with the id, and `nullsLast` puts empty values last in both directions. Trade-off: a cursor holds the sort values of the last row seen, so inserts and deletes never shift other rows, but a row whose sort value changes while someone pages can appear twice or be skipped in that pass.
- **Scalars.** `Date` is a calendar day, `YYYY-MM-DD`, and stays a string end to end. `DateTime` is an instant: ISO 8601 with a time zone in, UTC ISO out, and a JS `Date` inside the API.
- **Server:** Express 5 and Apollo Server 5 via `@as-integrations/express5`, at `/api/graphql`. Every API route lives under `/api/`; only the health probes `/healthz` and `/readyz` sit at the root, and an unknown `/api/` path is a 404, never the web app. Depth limits, bounded pagination, introspection off in production, error masking configured explicitly.
- **Mutation names** follow [RULE26](code-quality.md#api), such as `employee { create }` and `company { removeLogo }`.
- **File uploads** (spreadsheet import, the company logo) use a bounded REST endpoint, not GraphQL: the logo is `PUT /api/company/logo` and a staff file `POST /api/imports/files?name=…`, each with the raw file as the body, stored as a file (see Files in §4). An uploaded Excel workbook is parsed in a worker thread with capped memory and a timeout, never on the API's main thread, so a hostile file fails on its own. A PDF is parsed in a worker thread too, inside a child process whose whole memory the OS caps at 512 MB (`prlimit --data`, without a shell; Node run `--jitless`), because pdf.js keeps decoded streams outside the worker's heap; macOS does not enforce the cap. PyMuPDF reads the same PDF's word boxes in a second child process under the same limits (`packages/pdf-words`, Python): bytes in on standard input, JSON out, an environment without secrets, and text drawn invisibly left out. Heavy reads run one at a time. No subscriptions.

## 3. MCP

Broccoli exposes a [Model Context Protocol](https://modelcontextprotocol.io) server so the operator's own agent can read and act on company data.

- **Tools are hand-written over shared use cases.** GraphQL resolvers and MCP tools are two thin adapters over the same application layer. Permissions, field visibility and audit are enforced in the application layer, so an MCP tool can never do more than the GraphQL API allows.
- **Small catalogue.** The first release has about ten tools: search, read and update people, field definitions, reporting lines, and the import steps `start_import`, `upload`, `set_mapping`, `preview_import`, `commit_import`. Import drafts live in Postgres; parsing is deterministic and the agent proposes column mappings. No model key is needed on the Broccoli side.
- **Consequential writes need browser approval.** Committing an import requires the user to approve an exact draft revision in the web app. A tool argument such as `confirmed: true` proves nothing. Edits invalidate the approval; commit is idempotent and re-checks permissions.
- **Transport and auth.** Stateless Streamable HTTP via `@modelcontextprotocol/express`. OAuth 2.1 with PKCE (see §6) with read-only or read/write grants, intersected with the user's permissions. MCP resources and prompts are deferred.

## 4. Data access

- **Drizzle ORM**, pinned to the 0.45 line. The TypeScript schema is the single source of truth; `drizzle-kit generate` produces SQL migrations that are reviewed in each pull request. Hand-written SQL in migrations is allowed for extensions, triggers and constraints.
- Recursive CTEs (org chart, reporting lines), window functions and JSONB paths use the `sql` tag.
- Upgrading to Drizzle 1.0 (new migration folder format, Relational Queries v2) is a planned task after the first release.
- **One Postgres role** and one `DATABASE_URL`. The role owns the schema, so Broccoli runs on managed Postgres plans that offer no superuser. Migrations run at startup under a Postgres advisory lock, so instances starting together apply them one after another. The instance does not report ready until they succeed.
- **Transactions.** A use case opens one with `transact(work)`, the `runInTransaction(orm, eventBus, work)` the core binds once at startup, and passes the opaque `Tx` it gets to every operation that must join it, its own repositories (`companyRepository(tx)`) and other modules' public operations (`advanceStep(tx, …)`) alike. Operations meant to compose take a required `tx` ([RULE20](code-quality.md#layers-and-place)); there is no nesting and no savepoint, and a `Tx` used after its transaction ended throws. Only database adapters reach the ORM behind a `Tx` (`ormOf`), so ORM types stay inside them.
- **Files** live in Postgres: `core/files` keeps their bytes and MIME type in the `files` table, so a rollback undoes a stored file and a database backup includes it. Core knows nothing else about a file: no category, owner or access rule. A module stores a file with `storeFile(tx, …)`, keeps its id in its own table (a foreign key without cascade, so a referenced file cannot be deleted), serves it from its own route after its own access rule and a check that the id is one of its own, with `sendFile`, and deletes it with `deleteFiles(tx, ids)`. A file never changes; a new version is a new file, so its URL is cached for good. There is no generic download route.
- `pgvector` is added only when a feature needs it.

Kysely with generated types and Prisma were considered. Drizzle was chosen for a single source of truth and generated migrations; the cost is that generated SQL must be reviewed.

## 5. Events, jobs and workflows

- **Postgres only, one engine.** A transactional outbox table is written in the same transaction as the mutation and its audit row. **pg-boss** drains the outbox and runs all background jobs and cron.
- Delivery is ordered per entity; consumers are idempotent. No timers, no second workflow engine, no external queue.
- **Until the outbox lands**, domain events are delivered in process. A publisher queues a domain event on its transaction (`tx.publish(type, payload)`); `runInTransaction` dispatches the queue after the commit and drops it on rollback. Handlers run one after another and are awaited, so the request answers after them; a failing handler is logged, never passed to the publisher. Event types are declared by their publisher by declaration merging on `DomainEvents`, and modules subscribe through their manifest's `events`. A crash between commit and dispatch loses the event, which is accepted for now; the outbox will write the queue in the transaction instead, without changing publishers or handlers.
- **Jobs.** pg-boss runs in the API process, its queue in the instance's Postgres (`pgboss` schema, which it creates and migrates itself); it starts after the migrations and `/readyz` reports ready only then. A module declares its job names and payloads by declaration merging on `Jobs` in `core/jobs`, queues a job with `jobs.send(tx, name, payload)` inside its transaction, so a rollback drops it, and handles it through its manifest's `jobs` as the system. Each job gets three attempts with backoff and expires after two minutes unless its handler sets `expireInSeconds`, which also changes a queue created earlier; after the last one, or when it expires or dies with the process, the handler's `onFailed` runs. Handlers are idempotent and check that the job is still current.
- Workflows such as approvals and onboarding are state machines in the domain; each step is a job.

## 6. Auth and sessions

- **Better Auth** with the Drizzle adapter, mounted before body parsers. Only the plugins in use are enabled; packages are pinned together.
- **Sessions** are opaque, database-backed and carried in Secure, HttpOnly cookies, with CSRF protection and cookie caching off. Logout, account disabling and permission changes take effect immediately. A session lasts 7 days and is renewed daily while in use; GraphQL, which every page calls, passes the renewed cookie on to the browser; other HTTP routes do not renew. The web app reads the signed-in user from `Query.me`.
- **MCP clients** authenticate with OAuth 2.1 through `@better-auth/oauth-provider` and `@better-auth/mcp` (discovery, PKCE S256, client registration, audiences, refresh, revocation). An application-level active-grant check makes revocation immediate.
- **Mode.** `BROCCOLI_MODE` is `self_hosted` (the default) or `managed`. It is deployment configuration, so it lives in the environment, not the database.
- **Managed init.** A managed instance boots with `MANAGED_INSTANCE_ID` (its pool slot) and `MANAGED_ACCOUNTS_URL` (default `https://accounts.getbroccoli.com`) and waits. Orchestration assigns it with `POST /api/init`: an EdDSA token from that issuer, audience `instance:<MANAGED_INSTANCE_ID>`, purpose `init`, living at most a minute, carrying `{ companyId, publicOrigin, websiteOrigin }`. The assignment is stored on the `instance` row once; the same request again is accepted, a different one refused. Until then `/readyz` reports `initStatus: waiting` and user routes answer 503. Better Auth is built from the stored assignment on first use, so an assigned pool instance needs no restart.
- **Managed sign-in.** A Better Auth plugin: `GET /api/auth/managed/start` sets a state cookie and sends the browser to the website's entry page with the company id; the website posts a ticket from the accounts service to `POST /api/auth/managed/callback`. The ticket is checked (EdDSA, issuer, audience = the public origin, at most a minute, the website's exact Origin, state = cookie), its `jti` is used once in the transaction that finds the owner by subject, never by email, or claims the owner on a new instance, and a normal session is created. Failures redirect to `/login?error=…`.
- **Slack connection.** The owner connects Slack through the OAuth relay on the accounts service at `SLACK_RELAY_URL`, which holds the Slack app's secret, so an instance needs no Slack secret. It defaults to the development accounts service until the production one is live. `GET /api/integrations/slack/connect` keeps a random state and a PKCE verifier in a ten-minute HttpOnly cookie and sends the browser to the relay; the relay returns to `/api/integrations/slack/callback` with a one-time handle, which the instance redeems from the server with the verifier. The relay accepts any return address, so the state check and PKCE are what bind the answer to the browser that asked. The `slack` module owns the connection and its encrypted token; connecting reads nothing. Other modules read the workspace through its public use cases (`readSlackMembers(ctx)`, then `isCurrentSlackConnection(ctx, tx, snapshot)` in their transaction), as the import does when the owner imports or refreshes its members.
- **Setup.** A new instance goes through the steps `company`, `import`, then on self-hosted instances `owner`, and ends at `done`; the `instance` row holds the step.
  - Self-hosted instances have no public sign-up. `POST /api/auth/setup/start`, a Broccoli plugin on Better Auth, gives the first browser the setup session: a random token in an HttpOnly cookie, its hash on the `instance` row, valid three days after the holder's last start. Every other browser is refused, also after expiry, until the database is dropped.
  - That browser acts as the setup holder. Use cases of the setup steps (company, import, Slack) admit it with `ctx.requireSetupAccess()`; everything else refuses it.
  - `POST /api/auth/setup` creates the owner's user, password and session for the holder at the `owner` step, completes setup and ends the setup session, in one transaction that locks the `instance` row. All setup endpoints are rate-limited per address and refuse other origins.
  - **Demo.** Instead of the import, `POST /api/auth/setup/demo` makes the holder a provisional owner: a real user with a placeholder email in the reserved `.invalid` domain and no credentials, signed in with a normal session. In one transaction it claims the owner, runs the demo start the `imports` module provides through its manifest (which completes setup now that an owner exists and fills the demo company), sets `instance.demo_expires_at` seven days ahead and ends the setup session. The provisional owner is a normal owner, so no use case needs a demo branch; only clearing demo data refuses while the demo runs. The deadline never moves: session resolution refuses the owner's session once it has passed, whatever Better Auth's renewal says, and no enabled Better Auth endpoint can add credentials. Before it, `POST /api/auth/setup/account` gives the same user an email and password, replaces their sessions and clears the deadline, so the user id, and everything recorded during the demo, stays. Or `POST /api/auth/setup/demo/reset` ends the demo: in one transaction it deletes the demo's people through the `demo` module's manifest, the provisional owner and their sessions, moves setup back to the company step and gives the browser a new setup session; the company and AI choice stay. After the deadline nobody can sign in, and only a new database frees the instance.
  - The web root starts or renews setup once per page load and sends every other browser to `/setup/in-progress`; the gate sends the holder to the page of the open step.
  - Managed instances have no setup endpoints: the first valid sign-in ticket claims the owner. The owner is identified by the user id, not the email.
- **Passwords** are 8 to 128 characters.
- **Owned by Broccoli, not the library:** owner bootstrap and recovery, invitations (email, later Slack), act-as impersonation (real actor and effective profile stored server-side, both audited, no credential or grant changes while impersonating), password policy.

## 7. Permissions and audit

- **Permissions** combine row scopes (`self`, `team`, `reporting_line`, `all`) per object with field visibility (`public`, `protected`, `sensitive`). Both are enforced in the application layer: use cases receive a security context and grants, repositories apply scope predicates before pagination and counting, and results are projected to readable fields before leaving the use case. Filtering and sorting cannot reveal hidden fields. Signing in is the adapters' concern, so application code always receives a `SecurityContext` and decides only what it may do. Work Broccoli does on its own runs as the system (`PrincipalSecurityContext.system()`), never without a context. GraphQL denies by default: the `GraphqlContext` carries a nullable `security`, every root field without the `@public` directive refuses a request without a session before its resolver runs, and a resolver passes `context.getActor()` to its use case; only `@public` fields (`ping`, `setup`, `me`) work without a session. HTTP routes and MCP tools call `requireSignedIn(security)` too. Until scopes are built, application code calls `ctx.requireOwnerOrSystem()`: the owner and the system have scope `all`, everyone else nothing.
- **Audit.** Every mutation emits a domain event carrying the real actor (including impersonation), the client (web, MCP or job) and a trace id. Events land in an append-only `audit_log`; a trigger rejects updates and deletes. There is no generic field history in the first release.
- **Custom fields** are deferred to their own module design. The only decision now: no runtime DDL.

## 8. Frontend

- **Vite single-page app** with React 19, served as static files by the API container with a deep-link fallback. No server-side rendering.
- **TanStack Router** with file-based routes and automatic code splitting; `routeTree.gen.ts` is generated by `pnpm codegen` and not committed. A pathless `_authenticated` layout with a `beforeLoad` redirect to `/login?redirect=…` is the auth gate and renders the shell. Until setup is done, the root route and the gate send each browser to its setup page (see Setup in §6). Setup pages use `SetupLayout`; other pages outside the shell use `AuthCard`. An Apollo error link sends any `UNAUTHENTICATED` response through the gate. Filters, sorting, pagination and wizard state live in validated search params.
- **Apollo Client 4** with the default normalised cache and data masking. Operations are `.graphql` files next to the feature that uses them. `@graphql-codegen`'s client preset reads the API's SDL files (introspection is off) and writes typed documents to the gitignored `src/__generated__/`, imported by file path. Every object type exposes `id` ([RULE34](code-quality.md#frontend)). `possibleTypes` and `{ merge: true }` type policies for namespace types, the `id`-less types that root fields return, are generated at codegen time. Components own colocated fragments ([RULE33](code-quality.md#frontend)), such as `EmployeeNameCell_employee`; queries spread them, and data masking keeps their fields private. Creates and deletes refetch the affected list queries. The cache is cleared (`clearStore`) on sign-in, sign-out and act-as. Components query with `useQuery`; router loaders do not prefetch. The one exception is the `Session` query (`me` and `setup`), which the root route's `beforeLoad` runs on every navigation and passes on as route context for the gates.
- **UI kit:** shadcn/ui in the `base-nova` style on Base UI (triggers take `render`, not `asChild`), Tailwind v4 with design tokens as CSS variables in `styles.css`, Phosphor icons ([RULE39](code-quality.md#frontend)). The Hanken Grotesk font is bundled, so the browser makes no third-party requests. Light theme only for now.
- **Lists:** content lists use the shared `DataTable` in `components/dataTable/`, fed a column set by the feature, and `useListPage` in `lib/listPage/` for search, sort and cursor paging in the URL. The feature keeps its search schema, query and copy.
- **Shell:** a window-sized frame with navigation above the Canvas on narrow screens and on the left on desktop. The Canvas is a card that owns its own scroll; the document never scrolls.
- **TanStack Form** with Zod schemas, shared with API input validation where practical, and shadcn/ui components.
- **State:** see [RULE37](code-quality.md#frontend).
- **i18n:** English only, with every string ready for translation from day one ([RULE36](code-quality.md#frontend)).
- **Dates are strings** ([RULE29](code-quality.md#data-configuration-and-logs)): codegen maps both scalars to `string`, because `new Date("2026-10-10")` is UTC midnight and shows the previous day west of UTC. A calendar `Date` is displayed by formatting the timestamp `Date.UTC(y, m - 1, d)` with `timeZone: "UTC"`.
- Routes and the shell compose features ([RULE38](code-quality.md#frontend)); a feature imports another feature only where `importRules.json` lists it.
- Pure frontend functions get unit tests; no component or browser tests yet.

## 9. Testing

- **Vitest** everywhere, in three layers. Domain unit tests sit next to the code. Use-case integration tests (`*.int.test.ts`) sit next to the use cases and call them directly against a real Postgres; they carry most of the behaviour. End-to-end API tests under `packages/api/test/e2e` start the real server and call it over HTTP to prove the wiring.
- **Isolation.** One template database is migrated once per run; each test gets a fresh database cloned from it, so files run in parallel. Database names carry a per-run id, so several runs can share one Postgres server.
- **Test data** comes from `TestSeed`, which inserts through each module's repository and skips the use cases, so setup never depends on the code under test and writes no audit rows or events. The demo company lives in the `demo` module, not in test seeds.
- **Property-based tests** are used sparingly and agreed case by case (access rules are the first candidate).
- MCP gets smoke tests after the first release.
- **Evals** (`*.eval.test.ts`) run the product's AI decisions against the real model, on demand with a developer's key; they are not part of CI.

## 10. Tooling and layout

- **pnpm** workspaces and **Turborepo**, remote cache off.
- Packages live under `packages/`: `api`, `web`, `updater`, `scripts`, `pdf-words` and shared packages, which are added when there is code to share.
- **One Python package.** `pdf-words` is Python because PyMuPDF's word boxes are what the PDF extraction was measured with. uv pins Python and its packages in `uv.lock` and `pnpm install` sets them up; ruff lints and formats it and pytest tests it through the package's `lint` and `test` scripts, which `pnpm check` runs. ESLint, the import rules and jscpd cover TypeScript only.
- The repository root stays short ([RULE8](code-quality.md#modules-and-files)): the workspace files, the Compose file and `.env.example` are the tool files there.
- **Builds.** The web app builds with Vite and the API with tsdown, so TypeScript resolves imports like a bundler, which is what lets imports follow [RULE2](code-quality.md#modules-and-files).
- **ESLint** (typescript-eslint, import rules from `importRules.json` through `eslint-plugin-boundaries`, `@graphql-eslint` for the web app's GraphQL documents) and **Prettier**. **jscpd** fails `pnpm check` on code repeated outside tests.
- **Scripts** are kept to a minimum: `packages/scripts/dev.sh` and `packages/scripts/prune.mjs`. Everything else is a pnpm script or a Compose file. New scripts are added only for a demonstrated need.
- **CI** on GitHub Actions: format, lint and type check; unit tests; end-to-end tests against a Postgres service; secret scanning. Jobs that need Docker services run on self-hosted runners inside a container and reach services by hostname, never through host ports.

## 11. Development environment

- `docker-compose.yml` is the self-hosting file: Postgres, the Broccoli image (built from `packages/api/Dockerfile`) and, later, the updater. `docker compose up` needs no `.env`, serves Broccoli on port 8080 and, through a one-shot `ready` service, prints its address once it is healthy. `packages/scripts/docker-compose.dev.yml` overrides it for development: `api` runs `tsx watch`, `web` runs the Vite dev server and proxies API paths to `api`. Its watcher polls every 300 ms because host file events can be lost across Docker bind mounts. For both services, the checkout is bind-mounted with the `node_modules` that `dev.sh` installs on the host, containers run as the host user and development data has its own Postgres volume. pnpm and uv are needed only for development; self-hosters run `docker compose up`. The development `api` container is the Dockerfile's `dev` stage, Node with uv, and installs the word reader's Python environment for itself over the host's.
- Compose names the project after the folder, so each checkout or worktree gets its own containers, volumes and network. Host ports come from the gitignored `.env` (`HOST_WEB_PORT`, `HOST_PG_PORT`) with defaults in `.env.example`. `HOST_WEB_PORT=0` picks a free port, so the production image runs from any worktree with `HOST_WEB_PORT=0 docker compose up --build`.
- `pnpm dev` runs `dev.sh`, which starts the development stack on a free host port unless `HOST_WEB_PORT` is set, prints the URL and follows only new logs. Successful startup and shutdown output is hidden; a failed command prints its output. It traps exit and runs `docker compose down`, so Ctrl-C, errors and normal exits all tear the stack down; volumes are kept. `pnpm dev --drop-db` first removes the development Postgres volume labelled with this checkout, so it starts on an empty database.
- `pnpm dev:prune` removes Compose projects whose checkout no longer exists. The development Postgres volume is labelled with its checkout folder; unlabelled projects are never touched.
- End-to-end tests use the same Compose file with a `test` profile for a throwaway Postgres. Its host port is picked freely unless `HOST_PG_PORT` is set, and the tests find it with `docker compose port`.

## 12. Configuration, secrets, observability and self-hosting

- **Configuration** is environment variables validated with Zod at startup (blank counts as unset), one `env.ts` per package, no configuration files. Feature flags are plain environment variables. Startup refuses the other mode's prefixed variables ([RULE30](code-quality.md#data-configuration-and-logs)), so no fact has two sources.
- **Data folder.** `DATA_DIR` (default `/data`, a Compose volume) holds files that must survive restarts. `SELF_HOSTED_PUBLIC_URL` is the address browsers use; unset, Broccoli trusts the address of each request. Session cookies are Secure when `SELF_HOSTED_PUBLIC_URL` is https; without it the protocol is unknown, so they are not.
- **Secrets.** On first boot the app generates the encryption key and cookie secret into a volume file (`/data/secrets/`, mode 600) and reads them on later boots; `ENCRYPTION_KEY` in the environment overrides the file. Third-party credentials (Slack and similar) are stored in the database encrypted with the encryption key (`createSecretBox` in `core/secrets`, AES-256-GCM). The rule: the database holds hashes and ciphertext, never keys. Operators back up the secrets volume together with the database.
- **Brand lookup.** `BRAND_LOOKUP_URL` is unset by default, so a self-hosted instance makes no third-party call and suggests the company name from the owner's email domain only. Managed instances set it to a service that is not public; when set, Broccoli sends the owner's email domain, never the address, once, and stores the name and logo it gets back.
- **Logging** with pino: identifiers, not contents ([RULE31](code-quality.md#data-configuration-and-logs)).
- **Observability:** `/healthz` and `/readyz` (ready only after migrations). No third-party error service.
- **Self-hosting.** One image containing the API, the static web app and migrations, published to `ghcr.io/getbroccoli/broccoli` for every commit on `main` and on pull request branches, tagged with the short commit SHA; the API serves the web app from `WEB_DIR` and answers other page paths with `index.html`. Postgres from Compose, with trust auth on the Compose network and no published port; publishing it requires a password first. An updater sidecar that pulls a tag, pins the image by digest, health-checks and rolls back. Backup is documented `pg_dump`, not a built-in feature.
- **Managed** installs use the same image with `BROCCOLI_MODE=managed`, `MANAGED_INSTANCE_ID` and `OPENROUTER_API_KEY`, Broccoli's key for the model provider; their company, address and website come from the signed init (§6), not the environment.
- **AI.** `integrations/ai` is the only way a request reaches a model: the decisions API, multiple-choice questions about a JSON state sent to OpenRouter's decisions endpoint, each answer with a confidence (under 0.8 counts as no answer). Each request picks its source. A managed instance always uses OpenRouter with `OPENROUTER_API_KEY`, which it requires. A self-hosted owner picks the source at setup ("Setup AI"): Broccoli AI at `SELF_HOSTED_BROCCOLI_AI_URL`, a relay on the accounts service that speaks the same decisions API without a key, or OpenRouter with a key they paste, stored encrypted on the instance row and used before `OPENROUTER_API_KEY`. Their choice wins over the environment; before they choose, a key in the environment means OpenRouter, else Broccoli AI. Choosing checks the source first: OpenRouter's current-key endpoint for a key, a token from the relay for Broccoli AI. On its first decision a self-hosted install asks the relay for a token (one per address, free for a limited period), keeps it encrypted in `DATA_DIR/secrets/broccoli-ai-token` (mode 600) and asks again once when the relay no longer knows it. The token survives database resets without extending the trial; an older token on the instance row moves to this file on first use, and the file takes precedence over a restored database backup. A refusal that waiting cannot fix fails the file with the provider's own words, or, when Broccoli AI's free use is used up, with a reason the page words itself and a way to add an own key. Callers follow [RULE31](code-quality.md#data-configuration-and-logs): a file's first rows, not the file. Personal data never leaves as itself: before each request, every string in the state that could identify someone becomes a placeholder of the same form (`Xxxx Xxxxx`, `person1@…`, `dd.dd.1988`), deny by default, and every request asks OpenRouter for providers that keep nothing.
- **PDFs** are read through masked completions instead: `createReferenceCompletions` sends OpenRouter's chat completions API one of four tasks the PDF extraction registers at startup (select candidate rows, qualify a layout, extract word references, assign emails), each with its fixed instructions and JSON schema. The extraction reconstructs layouts locally from both readers and sends only masked evidence: an id, a box, a shape (`Xxxx`, `DD.DD.DDDD`) and a fixed category per word or cell, and drafts of ids; the model answers with indexes and ids, and code restores the values locally. `parseCompletionInput` refuses any other content before a request is made. Every request names the model and asks for zero data retention, no data collection and providers that honour every parameter; a failure worth repeating is retried once with other providers. Broccoli AI answers no completions, so a PDF needs OpenRouter. A run has five minutes, and its mapping job six.
