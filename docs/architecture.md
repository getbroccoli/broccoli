# Architecture

This document records Broccoli's architecture decisions and their reasons. It is edited in place; the git history is its change log. Its scope follows [RULE61](code-quality.md#docs-and-comments).

## Layout of the API

```
packages/api/src/
├── core/          shared infrastructure, instance-wide concerns and the primitives features build on
├── modules/       business modules, one folder per domain
├── integrations/  clients of external services; know no business module
└── utils/         helpers that know nothing about Broccoli
```

Each package declares its allowed dependencies, enforced by lint with no cycles ([RULE2, RULE3](code-quality.md#modules-and-files)). Core never imports a business module; startup composes them through their public surfaces.

## 1. Shape of the system

- **Modular monolith.** One API process, one web single-page app, one container image. Business modules own their rules; integrations own external transport. This keeps deployment simple without giving up module boundaries.
- **Single-tenant.** One deployment and one Postgres database per company, for self-hosted and managed instances alike. There is no tenant column or row-level security; the managed service runs and migrates each instance separately.
- **Layers per module** separate business decisions, persistence, application coordination and transport, as described below. State-owning parts of core follow the same structure.
- **Composition.** Startup supplies each module with only the dependencies it needs and collects its API, routes, event handlers and jobs. Modules communicate through public operations or events, never through another module's tables ([RULE21](code-quality.md#layers-and-place)).
- **Domain-driven design is tiered.** A plain domain layer with unit tests is the default. Aggregates, value objects and domain events are introduced where invariants demand them, with each business decision owned in one place ([RULE52](code-quality.md#layers-and-place)).
- **Demo data.** The demo module owns the sample company and coordinates other modules' public operations in one transaction; it owns no tables. Exiting the demo removes the sample company and people added during it, then returns to setup. A regular owner keeps their account; a provisional owner follows the separate lifecycle in §6.
- **Four primitives.** HR features share records, tasks, calendar and processes, so each feature does not grow its own task queue, history and approval engine. A record stays a typed entity in its owning module; shared capabilities do not turn records into a generic storage engine. Shared record capabilities live in `core/records`, which modules use without core knowing them; history is the first. Tasks and processes live in core beside records, and features plug into them through registrations and contracts they fill, so core never imports a module. Tasks are in `core/tasks`: a person, a feature or a process step asks one person for work, its assignee marks it done, and only the person who asked deletes an open to-do; a process's task names who asked without letting them delete it, and a task never grants authority. Processes are in `core/processes`: a published version of a process says when it starts and which steps give whom a task; each run of it follows those tasks to its end. A record type a run may be about registers how processes read it (who it is about, its dates), the module that publishes an event registers it as triggering, and the employees module fills the people and working-calendar ports processes reads through. Notifications are in `core/notifications`: a process step's `notifications.notify` action names who to tell, by an employee field of the run's record, and an email template the record's module registers; a job reads the record as it is then and emails the employee if they joined and may still see it. Built-in processes decide who is told about what, so tasks send no email themselves. Approvals are in `core/approvals`: a feature asks for approval of its record by naming an approval process, which processes runs like any other, and hears the outcome through `approvals.approval_finished` before the commit of the decision; approvals owns no tables and no workflow. Calendar is not built yet. Domain-specific rules, such as leave balances, stay with the feature that owns them.

### Module layers

Layers live inside the module that owns the feature. For example, a company logo upload belongs to the company module even when setup first uses it. Shared technical folders hold concerns with no feature owner. This organization keeps business decisions usable from every transport and testable without a database, while persistence and transport can change independently ([RULE56, RULE17](code-quality.md#layers-and-place)).

- **`domain` — business decisions.** Holds business facts, invariants, calculations and valid state transitions. It works on domain values without I/O or knowledge of storage, requests or frameworks. A business decision has one owner here, so every caller applies the same rule.
- **`db` — persistence.** Owns tables, queries, persistence constraints, locking and mapping between stored data and domain objects. Repositories hide SQL and ORM details and return whole domain items, with encrypted secrets and facts derived from other records read separately, so callers do not assemble business state from storage fragments.
- **`app` — application coordination.** Use cases and services coordinate authorization, domain decisions, repositories, integrations, transactions and events or jobs. This layer owns the operation's workflow and transaction boundary. It gathers the facts a domain decision needs and applies its result without duplicating that decision.
- **`ports` — what a module needs from others.** Interfaces the module's `app` reads through, which another module implements, such as the people processes reads. Keeping them in their own folder shows each module's outside dependencies at a glance.
- **`adapters` — implementations of another module's ports.** Each adapter fills a port with this module's services and repositories; startup hands it to the module that owns the port.
- **`graphql`, `http`, `mcp` — transport adapters.** Handle request parsing, caller identity, transport-specific responses and error translation. They delegate operations to the application layer, so permissions and business behavior remain the same for the web app and agents.
- **`helpers` — module-local technical work.** Holds concerns such as parsing an origin or hashing a secret. Every layer may use these helpers, which cannot depend back on those layers. This keeps technical concerns out of the domain model; helpers with no Broccoli knowledge belong in `utils`.

Dependencies point inward: transport and `adapters` → `app` → `db` → `domain`; `app` also uses `domain` and its own `ports` directly. Layers expose their public contracts through their folder's entry point. The allowed imports are enforced, rather than relying on convention ([RULE16, RULE17, RULE58](code-quality.md#layers-and-place)).

**Use cases and services.** A use case represents an action a caller can perform. Related operations on one subject form a service, keeping that subject's lifecycle and formats together; every `app` subject is a service, even with one operation. Adapters translate each operation into one use-case call and retain only transport concerns such as cookies and redirects ([RULE18](code-quality.md#layers-and-place)).

**Applying the boundaries.** Authorization belongs to the use case even when an adapter already authenticated the caller. The use case owns the transaction; composed operations share it, and database adapters supply the locks and constraints that keep concurrent writes safe. External calls stay outside database locks. Repositories that reference a stored file call core's file storage service in their own write: it is shared storage with no authorization or workflow, the one place `db` calls `app`. These choices keep an operation consistent across transports and under concurrency ([RULE19, RULE20](code-quality.md#layers-and-place)).

For example, a domain rule decides whether an import source may retry. The application layer checks the caller and coordinates the retry; the repository persists the change under the required concurrency checks, and the adapter presents the result. The decision is not repeated in a resolver or SQL query ([RULE52, RULE60](code-quality.md#layers-and-place)).

## 2. API

- **GraphQL is the primary API**, currently an internal contract for the web app. It may change before 1.0; there is no published schema or deprecation policy yet.
- **Schema-first.** Modules own their SDL and resolvers, composed into one schema. Generated types connect the API and web app to that contract.
- **Connected graph.** Related types link in both directions so components can select their data through fragments without adding root queries ([RULE23](code-quality.md#api)). Related-object reads use request-scoped batching to avoid N+1 queries ([RULE25](code-quality.md#api)).
- **Mutation payloads** carry the changed object, or its parent after removal, and typed expected failures. This lets clients select the result in the same request and lets contracts grow without changing unrelated operations ([RULE24, RULE27](code-quality.md#api)). Authentication, authorization, query and pre-execution failures remain top-level GraphQL errors; unexpected errors are masked.
- **Update inputs: left out, null, a value.** An update input names only the fields to change, and each changeable field is optional. A field left out stays as it is, `null` clears a field that may be empty, and a value sets it. GraphQL keeps the difference: a left-out field is absent from the resolver's input, and an explicit `null` is present. The service reads `undefined` as "keep" and `null` as "clear", and refuses `null` on a field that can't be empty, as invalid input on that field. A field that must always hold a value on create stays required there. The input's description states the rule ("The fields to change; a field left out stays as it is, and null clears a field that may be empty.").
- **Namespaced mutations** group operations by module: one namespace per module, named after it. GraphQL guarantees serial execution only for root mutation fields; nested fields may run in parallel. The server therefore permits one namespace and one operation per mutation. Naming follows [RULE26](code-quality.md#api).
- **Pagination.** Lists use Relay connections over keyset queries with a stable order and a unique tie-breaker. Cursors are opaque and bound to their sort order. Inserts and deletes do not shift other rows, but a row whose sort value changes during paging can appear twice or be skipped in that pass.
- **Dates.** A calendar date stays a `YYYY-MM-DD` string end to end. A date-time represents an instant, accepts an explicit time zone and returns UTC ([RULE29](code-quality.md#data-configuration-and-logs)).
- **Transport.** Express and Apollo serve the API on the web app's origin. API routes are separate from health probes and the web fallback. Query depth and page sizes are bounded; production introspection is disabled. There are no subscriptions.
- **Files** use bounded HTTP uploads. Untrusted workbook parsing runs in a worker with memory and time limits, so a hostile file cannot occupy the API's main thread.

## 3. MCP

[Model Context Protocol](https://modelcontextprotocol.io) is the API a person's own agent, such as Claude, ChatGPT, Claude Code or Codex, uses to read and act on company data as that person.

- **Shared application layer.** MCP tools are thin adapters over the same use cases as GraphQL, with the same permissions, field visibility and audit. A small, purpose-built tool catalogue avoids exposing the entire schema as tools.
- **Writes the person saw.** An agent writes only the person's own records, such as their leave, and only what the person could change in the browser; deciding a task they hold, such as approving someone's leave, happens only on the approval card below. A write repeats what the agent showed the person, such as leave's total cost from its preview, and saving refuses another total; showing the dates and asking the person first is the agent's instruction, not something the server can check. Whatever needs approval waits for a person's decision: in the web app, or on a card the agent shows in its chat (MCP Apps), whose button carries a one-time token Broccoli hands the card beside the model's view; the task refuses an agent's decision without it, so an agent never decides on its own, and its claim that a user confirmed is not approval. A chat app that drops the token shows the card without buttons, with the link. Broccoli trusts the chat app to keep the token from the model and to send it only from the card: a client could press for the person, which is why the card exists only for connections the person allowed to change things.
- **Setup access stays separate.** The owner's coding agent during setup keeps its one-time code and dedicated HTTP routes; its session is limited to setup and never becomes a person's agent connection.
- **Transport and authority.** Stateless Streamable HTTP at `/api/mcp`, authorized by OAuth 2.1 with PKCE. Better Auth's OAuth provider is the authorization server at `/api/auth`, for public clients registered dynamically or through a client metadata document. Tokens are opaque and checked in the database on every call, so an ended connection is refused at once; each call resolves the person's security context afresh, as for their browser, and a token must name this instance's MCP address as its resource. Two scopes, read and write, are intersected with the person's permissions; each tool declares the scope it needs, and the security context carries the agent's connection and scopes, so shared use cases refuse a write without write scope and history names the person, through their agent. A connection allowed to read is asked to allow again before its first write; allowing again keeps the connection. The approval card is the one resource; prompts remain outside the scope.
- **One connection per person.** Allowing an agent ends the person's other agents' tokens and consents; a password reset ends them all. A token is issued within the browser session that allowed it, so the server detaches tokens from expired browser sessions before issuing new ones, and the connection outlives the browser's sign-in.
- **Agent activity.** Each tool call of a person's agent is recorded as one line: the tool, whether Broccoli answered, refused or failed, and a result count for searches; never what the agent read or asked. Calls whose token names no one are not recorded. Saving a line never changes the answer. Lines are kept 30 days.
- **Live updates.** A signed-in browser keeps one server-sent events stream open at `/api/live`. It carries only a nudge that the person's agent connection changed or their agent called a tool, never data; the page reads it again through GraphQL, so record scope stays in one place. Nudges follow the commit through the in-process event bus, and streams live in the one API process an instance runs.

## 4. Data access

- **Drizzle ORM.** The TypeScript schema is the source of truth for generated SQL migrations, which are reviewed. Hand-written SQL remains available for constraints, extensions and queries that need Postgres features. Kysely and Prisma were considered; Drizzle keeps one schema source, at the cost of reviewing generated SQL.
- **One Postgres role** owns the schema without requiring superuser access, for compatibility with managed Postgres. Startup migrations are serialized with an advisory lock; readiness waits for them to succeed.
- **Transactions belong to use cases.** Operations that compose join the caller's transaction explicitly. There are no nested transactions or savepoints, and ORM details stay in database adapters ([RULE20](code-quality.md#layers-and-place)). External work happens outside database locks.
- **Files live in Postgres**, so their writes roll back with the owning data and database backups include their bytes. The referencing module owns authorization and lifetime; references protect files from premature deletion. Files are immutable, allowing permanent caching of each version. There is no generic download route. External images are normalized before storage to bound serving costs and remove metadata.
- **Definitions that change over time are versioned.** A record people configure and others depend on, such as a working pattern, a time off policy or a process, keeps its content in a versions table beside it: each version is `draft` or `published`, with at most one draft per record. A draft is edited until it is published, its `revision` counting saves so publishing sees what the admin reviewed; a published version never changes, so whatever used it (an assignment, a process run) keeps meaning what it meant. A version stored as JSON carries its shape's number (`definition_schema_version`): parsing refuses a shape it does not know, and a migration that changes the shape rewrites every stored version, published ones included, without changing its meaning.
- **Extensions follow demand.** Vector search is introduced only when a feature needs it.

## 5. Events, jobs and workflows

- **Domain changes notify through events**, never injected callbacks or callback ports ([RULE72](code-quality.md#layers-and-place)). The publisher owns the fact and each receiving module owns its reaction, so adding a reaction does not add dependencies to the publisher or its callers. Work that must commit together uses direct public operations in one transaction.
- **Postgres is the durable work store.** pg-boss runs background jobs in the API process, using the instance's database. Enqueuing joins the business transaction, so rollback drops the work. Handlers run as the system, are idempotent and reject stale work; retries and terminal failures belong to the job lifecycle.
- **Scheduled jobs** are pg-boss schedules a module declares beside its job handler (a cron and a time zone); a missed occurrence runs once on the next start.
- **Events reach handlers at two moments.** Before the commit, a module's before-commit handler receives all of a transaction's new events at once, inside it, round after round while handlers publish more (at most ten rounds); its failure rolls the transaction back, so its reaction commits with the change or not at all. After the commit, in-process handlers run sequentially and are awaited; their failures are logged without undoing the committed operation, and a crash between commit and dispatch can lose an event, an accepted limitation for them. Rollback drops both.
- **Record changes publish `records.changed`**, one event per history line with the record, the operation, the changed field keys and the cause, never values. It notifies; processes trigger on domain events instead.
- **Durable delivery after the commit is a transactional outbox**, a pg-boss job queued with the business change (`jobs.send(tx, …)`), for reactions that are slow or call outside systems: a rollback drops the job, the commit makes it runnable, and it is retried. Processes with an `after_commit` trigger start their runs this way. This avoids an external queue or a second workflow engine.
- **Workflows** such as approvals and onboarding are domain state machines, with durable jobs executing their steps. A process starts from a trigger, never from a feature calling it: a record's date starts it by a daily job, and a domain event its publishing module registers as triggering (a person added, a task created or its status changed, an approval requested) starts it one run per event and record. By default it starts in the transaction that published the event, batched per process like a bulk save, and a run that cannot start fails that change; a process that runs after the commit starts from a job queued with the change instead, so its failures never fail the change. A step's task is finished with the ordinary task command; processes follows the task's status event before the commit and completes the step and the run in the same transaction. A transaction that locks a task and its run takes the task first.
- **A process acts as the system on its own and as the person when they act.** A run's own writes, such as creating its tasks or cancelling itself, run as the system with the run as their history cause (`PROCESS_RUN`); an assignee marking their step's task done, or an admin starting a run, acts as themselves under their own permissions. A step that runs an action another module registered runs it as the system, in the transaction that made the step ready, so an action only writes there and queues jobs for outside work; whether a step may act as someone else is not decided yet.
- **A run notices removals when it next runs.** Nothing reacts to a person's removal: a step still waiting on a task whose assignee was removed, or a removed subject, cancels the run the next time a command or the daily job touches it, and the cancellation commits instead of being thrown.

## 6. Auth and sessions

- **Better Auth** owns authentication and session mechanics, backed by Postgres through Drizzle. Broccoli owns owner bootstrap and recovery, invitations, impersonation and password policy.
- **Sessions** use opaque database-backed tokens in HttpOnly cookies, CSRF protection and no cookie caching. Revocation and permission changes take effect immediately. Cookie security depends on the configured public origin (§12).
- **Mode is deployment configuration.** Self-hosted and managed instances have different bootstrap and sign-in trust boundaries; the mode is fixed at startup, not stored as a user setting.
- **Managed initialization.** A trusted accounts service assigns an instance its company and public origins with a short-lived, signed, instance-bound token. Assignment is accepted once, with idempotent retries and conflicting assignments refused. User routes stay unavailable until assignment.
- **Managed sign-in.** Short-lived signed tickets bind the accounts identity to the instance and browser request. Issuer, audience, origin, state and replay checks protect that boundary. The owner is identified by the accounts subject, never by email. The first valid sign-in claims the owner; managed instances do not expose self-hosted setup endpoints.
- **Slack connection.** An OAuth relay holds the Slack app secret, so instances need no copy. State and PKCE bind the response to the requesting browser. The Slack module owns the connection and encrypted token. Reads happen outside transactions, with a check that the connection is still current before their results are committed.
- **Password reset** is Better Auth's flow, offered while the instance sends email: a self-hosted instance with a mail choice, or an assigned managed one. The token is stored hashed and lasts an hour; its email goes out from a job whose payload holds the token encrypted, so every address gets the same answer at the same speed and a failed send retries. A user without a password, such as the demo's provisional owner, never gets a reset email, since the reset would give them a password. Resetting ends every session of the user. Links point at the configured public origin, else the origin the email choice was saved from, never the requesting browser's.
- **Invites.** An admin invites people, with the profiles they will get; accepting an invite is the only way anyone but the owner gets an account. Each invite holds the SHA-256 of a 256-bit token, lives seven days, and one open invite per person replaces the last. The link carries the token in its fragment, so no server log or `Referer` sees it; it is emailed by a job whose payload holds it encrypted, or returned once to the admin to copy. Accepting creates the user with the employee's email and a password, gives the invite's profiles, links the employee and signs the person in, in one transaction that locks the invite row; every bad link gets the same answer. The lookup and accept endpoints are rate limited per address on self-hosted instances and per instance on managed ones, whose ingress forwards client addresses. Modules add such endpoints as Better Auth plugins through their manifest. Deleting an employee deletes the user who signs in as them. Setup's last step links the owner to the person they chose and invites the setup invite audience in the transaction that adds the people, so nothing is sent unless setup finishes.
- **Self-hosted setup.** There is no public sign-up. The first browser becomes the setup holder, with authority limited to setup operations. Setup stays locked to that holder even after the session expires. Owner creation, setup completion and the end of the setup session are atomic. Setup endpoints enforce origin checks and rate limits.
- **Acting as another employee.** A signed-in user may act as an employee their grants reach without using a profile they lack. Whom a session acts as is a column on Better Auth's session row, so it ends with the session's expiry or revocation; every request checks eligibility again and ends acting once it fails. Credential, consent and permission changes stay the signed-in user's own, at the auth endpoints and in use cases, and history names the signed-in user. The web app reloads every tab on start and stop and clears its cache when the session's identity changes, so one person's data never shows as another's. See [permissions](permissions.md#acting-as).
- **Provisional owner.** A self-hosted demo gives the setup holder a credentialless owner with a fixed expiry that session renewal cannot extend. Before expiry, exiting the demo atomically removes its people and provisional owner and returns the browser to setup. After expiry, the instance requires a fresh database. A demo cannot become a permanent account by adding credentials.
- **External agent authority is separate.** Setup agents exchange a short-lived one-time code for a limited bearer session; only hashes are stored. An installer with server access can connect before a browser holds setup and choose the external agent only while no AI source is saved. Access requires the external agent to remain selected, no owner to exist, setup to be before review and any setup session to remain live. Agent credentials authorize only dedicated agent operations and never fall back to browser cookie authority. One agent is active at a time. It receives masked mapping questions unless the owner permits an original file read (§12), and it cannot approve the import. Approval is tied to the revision the owner reviewed.

## 7. Permissions and audit

- **Authorization belongs to the application layer.** Adapters establish identity; every use case checks its security context. Background work has explicit system authority. GraphQL denies access by default, with narrowly designated public bootstrap fields.
- **Reporting lines are answered in one place.** Only the employees module reads an employment's direct manager; everyone else asks it for a person's manager, so positions or a cached manager change nothing outside it.
- **Permission profiles decide access.** Each signed-in user has `EMPLOYEE` plus any number of profiles of grants (actions on an object within a scope relative to their employee) and operations; managers get their rights from the reporting line, not a profile. Whether a write happens straight away or waits for approval is a write mode, answered in `core/records` from the same grants; features never decide it themselves and permissions hold no approval concept. See [permissions](permissions.md). Scope filters apply on each record's subject, before pagination and counting, and unreadable fields, once some exist, must not leak through results, filtering or sorting. All adapters share these rules.
- **Record history is one mechanism for every record type.** A use case appends its history lines in the transaction of the change, never from an event handler: each line holds the author from the security context, the cause, an optional reason and each changed field's old and new value. Records stay typed tables in their modules; a module registers each record's subject, core decides from it who may read the record and its history, and reads will filter hidden fields. A record no permission scope describes, such as a task its holder and the person who asked read, registers its own reading rule instead and is read-only through `access`. Lines are only appended, except that an explicit purge, such as Exit demo, deletes a record type's lines. An ordinary removal keeps the history and appends a deletion line.
- **Cloning is one mutation for every record type that allows it.** `records.clone` dispatches through the record type's registration, which creates the new record in one transaction; each module copies only its own tables, so terms take their working week from employees and their time off rules from time off. The versions the source works today are copied as drafts of new patterns and policies, so nothing is shared with the source; planned changes, assignments and history are not copied.
- **Audit records are append-only and separate from history.** The audit design records every action, including reads and refusals, with the real actor, effective identity during impersonation, client and trace; it will point at a history line instead of copying values. Impersonation cannot change credentials or grants. Audit is not built yet.
- **Custom fields do not use runtime DDL.** Their remaining design belongs with the feature that first needs them.

## 8. Frontend

- **React single-page app**, built with Vite and served by the API container with a deep-link fallback. There is no server-side rendering.
- **TanStack Router** owns navigation, authenticated routes and setup gates. Routes and the shell compose features; dependencies between features are explicitly constrained ([RULE38](code-quality.md#frontend)).
- **Apollo Client** owns server data through a normalized cache, generated operation types and component fragments with data masking. Session changes clear the cache so one identity never inherits another's data.
- **The cache follows mutation payloads, not refetches** ([RULE62](code-quality.md#frontend)). A payload returns what the change touched: changed objects update in place, and a delete evicts its record, which every connection then reads without. An addition is written into a cached list only where its place is certain: one fixed order and no filter, such as a record's history. Lists that are sorted, searched or paged on the server are not recomputed in the browser: they show a new or moved record when they next load. A refetch stays only for results the server computes, when carrying them in the payload would cost more code than the refetch saves, such as the import review's checks and pages. The trade-off: after a delete a page can show one row fewer, and after a rename an old order, until it next loads; this saves round trips, and the server's search and sort rules are never copied into the browser. Each feature keeps its cache writes in its `cache.ts` ([RULE63](code-quality.md#frontend)).
- **Update inputs send changes only.** A form builds its update input from its draft and the saved values: an unchanged field is left out, an emptied one is sent as `null`, and a changed one as its value. The generated input types (`field?: InputMaybe<T>`) allow both. The builder is a pure function with its own test, as `employeeDraft` is for the person panel.
- **State ownership.** Navigable state, such as filtering, sorting and paging, lives in validated search parameters. React state holds local UI state ([RULE37](code-quality.md#frontend)).
- **Shared UI.** shadcn/ui on Base UI, Tailwind design tokens and Phosphor icons provide the common UI. Lists share interaction patterns while features own their queries and validation. Fonts are bundled to avoid third-party browser requests. The initial theme is light.
- **Forms** use TanStack Form and Zod, sharing input validation with the API where practical.
- **Language and dates.** English is the first language, with user-facing strings ready for translation. Calendar dates retain their meaning in every time zone; date-times stay strings until display formatting ([RULE29](code-quality.md#data-configuration-and-logs)).

## 9. Testing

- **Vitest at three levels:** pure domain and frontend unit tests, use-case integration tests against real Postgres, and a smaller set of API end-to-end tests over HTTP. Most behavior belongs in integration tests.
- **Isolation.** Each test has an isolated database, allowing parallel runs. Fixtures use repositories independently of the use cases under test; external systems are the mock boundary.
- **UI checks are manual** for now, with no component or browser test suite. AI evals call real models on demand and stay outside ordinary CI.

Test design and execution belong in [testing.md](testing.md). UI verification starts with [QA setup](qa/setup.md).

## 10. Tooling and layout

- **pnpm workspaces and Turborepo** organize the monorepo. Packages live under `packages/`; shared packages are added when there is actual code to share. The repository root stays small ([RULE8](code-quality.md#modules-and-files)).
- **Builds** use Vite for the web app and tsdown for the API, with bundler-style TypeScript module resolution.
- **Automated quality checks** cover formatting, lint, types, module boundaries, duplicate code and tests. GitHub Actions also scans for secrets. Containerized CI jobs reach their isolated services over the container network.

## 11. Development environment

- **Compose mirrors self-hosting**, with development overrides for source mounts and live reload. Each checkout or worktree has its own services, network and persistent development data; dynamically assigned ports allow parallel stacks.
- **Development email works immediately.** Before printing its ready address, the development launcher configures Mailpit through the instance's mail settings service if no mail choice was saved. It preserves explicit choices and updates Mailpit links to the current development port. Settings shows the saved choice without browser-only defaults.
- **Shutdown preserves data.** Database reset is explicit, and cleanup targets only identified abandoned checkouts. Integration and end-to-end tests use a separate disposable Postgres instance.

Installation is in the [README](../README.md), setup in the [setup guide](guides/setup-guide.md), and test procedures in [testing.md](testing.md).

## 12. Configuration, secrets, observability and self-hosting

- **Configuration** comes from environment variables validated with Zod at startup. Mode-specific settings cannot compete with the other mode's settings ([RULE30](code-quality.md#data-configuration-and-logs)).
- **Public origin.** A self-hosted instance can use a configured browser-facing origin or trust the request address when unset. Secure cookies require an explicitly configured HTTPS origin; deployments must preserve that trust boundary.
- **Secrets survive restarts and database resets.** Generated encryption keys and cookie secrets live in restricted files in the data folder, outside the database. Third-party credentials are encrypted with AES-256-GCM; the database holds hashes and ciphertext, never encryption keys. Backups must include both the database and secrets volume.
- **Brand lookup is optional.** Self-hosted instances make no brand-lookup request by default. When enabled, the service receives only the owner's email domain, never the address, and the returned logo is stored locally.
- **Observability.** Structured logs use pino and carry identifiers, never contents ([RULE31](code-quality.md#data-configuration-and-logs)). Separate liveness and readiness probes distinguish a running process from one ready to serve after migrations and required services start. No third-party error service is required.
- **Self-hosting** uses one image for the API, static web app and migrations, plus Postgres on a private Compose network. Publishing the database requires password authentication. The updater design pins images by digest, checks health and rolls back failed updates. Backups use Postgres tools rather than a product-specific engine. Managed instances use the same image with centralized initialization and model credentials.
- **AI access is centralized.** One integration owns model transport. Managed instances use Broccoli AI with the credential their signed init carries, stored encrypted; self-hosted owners choose Broccoli AI, their own provider key or an external agent. An explicit choice takes precedence over environment defaults. Provider keys are encrypted; the Broccoli AI token persists outside the database so resetting it cannot extend the trial.
- **Email is an admin's choice.** On a self-hosted instance an admin chooses in the app between their own SMTP server, a Resend key, or no email, the default. The SMTP URL or key is encrypted and never returned; an SMTP server is checked by signing in before it is saved. One mail integration sends every email. Templates describe an email as blocks (heading, note, button and so on), which one renderer draws in Broccoli's layout (tables and inline styles, with the mark each instance serves itself); mailers are built per send from the saved choice so a change applies at once. There are no environment variables for it, as for the AI choice. A managed instance has no choice: it sends through Broccoli's mail relay with its instance credential, which takes the blocks, not HTML, and renders them with its own copy of the renderer, so a layout change ships in the relay first; it accepts links to the instance's own origin only and keeps daily quotas, and adds no reply-to; so an invite note sent through it may hold no link. No Broccoli email sets a reply-to.
- **Personal data is masked by default.** Mapping questions contain only the data needed for the decision, with identifying strings replaced before they reach a model or external agent. Model requests require providers that retain nothing. With an external agent selected, Broccoli makes no model requests.
- **Location names are a narrow exception.** The Company defaults page asks the model whose bank holidays apply at each location with the location names alone, unmasked, since place names identify no one; people's names, counts and every other value stay out of the request. A caller unmasks a value only by naming its top-level key (`unmaskedKeys`); every other request is masked as above. Without a model answer, such as with an external agent selected, each location falls back to England and Wales for the owner to check.
- **Original file read is an explicit exception.** The owner consents per file to its full contents, including personal data, going to the selected AI source. PDFs require this because their rows cannot be masked. Consent is bound to the displayed provider; a provider change or transfer from agent to model requires fresh consent. File names are never sent. Consent lasts until setup completes, including after Back from setup's last step.
